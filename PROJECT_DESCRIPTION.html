1. What it does

The project answers one question: if I have to drive down one of Gurugram's main roads, what time should I leave?

It covers 13 corridors — MG Road, Golf Course Road, NH-48, Dwarka Expressway, Sohna Road, KMP Expressway and seven others — and for each of them holds a congestion value for every hour of every day of the week. That is 13 × 7 × 24 = 2,184 slots. The site draws these on a map, colours each road by how congested that typical hour is, opens on the road and hour that save the most time, and shows Best time / Avoid chips plus a “You save” figure versus the quietest hour.

A trip planner lets a user type two real places. The route comes from TomTom Routing; where it overlaps a monitored corridor, the residual forecast is applied so the user can compare hours on an actual journey, not only on a named corridor.

The one number everything is built on

Every road, at every hour, is reduced to a single number called the congestion index:

congestion_index = 1 − (free-flow travel time ÷ expected travel time)
In plain terms

“Free-flow travel time” is how long the road takes when it is completely empty. “Expected travel time” is how long it is expected to take in that slot. The index is the fraction of the trip lost to traffic.

  • 0.0 — empty. You lose no time.
  • 0.2 — a fifth of the time is traffic. A 20-minute free-flow drive takes 25.
  • 0.5 — half the time is traffic. The trip takes twice as long as empty.

The index is always between 0 and 1, and bigger is worse. It is a ratio, not a speed, so a short stretch of MG Road and a long stretch of NH-48 can be compared on the same scale. Extra minutes versus empty are free-flow × index / (1 − index).

A raw decimal is not useful to a driver, so the index is converted into four labels. The cut-offs are round travel-time multipliers, not percentiles of my own data, so the boundaries do not drift as more rows arrive.

2. Why I built it the way I did

My first version generated its own traffic from a formula I wrote. It looked convincing and it was worthless — I was grading a model against numbers I had invented. I deleted that and rebuilt on measured TomTom readings only. Nothing in the repository is synthetic now.

That decision drove the rest. Real data is slow, gappy, and often less flattering than you would like. A lot of the engineering exists to deal with those facts honestly rather than to paper over them: fail with HTTP 503 if no model is loaded, never invent a fallback table, and only quote accuracy numbers that an evaluation script printed.

3. Where the data comes from

The baseline grid. bootstrap_collect.py swept the TomTom Routing API once for all 2,184 slots. Requesting a route with a future departAt and computeTravelTimeFor=all returns TomTom’s historical model for that road at that hour. I had planned to use Flow Segment Data; that endpoint returned 403 on this project’s key, so Routing became the only live and historical source. The limitation of this baseline is that it is date-blind: six future Fridays at 6 PM return the same answer, festival week included.

Live observations. collect_live.py polls the same API for travel time now and writes an observed index, plus:

  • weather from Open-Meteo (rain, trailing three-hour rainfall, visibility, temperature) — no API key
  • calendar features — Indian public holidays via holidays.India(subdiv="HR"), festival periods, month-end
  • incidents from TomTom Incidents, attached only if they fall within 300 m of the corridor’s digitised polyline

Collection ran on GitHub Actions as an hourly job that looped four rounds fifteen minutes apart (GitHub’s scheduler is unreliable at a 15-minute cron). After the residual model was trained on 15 October 2026, collection was stopped so the submitted snapshot would not keep drifting.

What has accumulated. The live CSV holds 24,490 rows from 16 August 2026 20:00 through 15 October 2026 16:00 — 61 calendar days, all 13 corridors, all seven weekdays. Training does not use every raw row. 3,119 were dropped because TomTom’s reported length was more than 2% off the mapped corridor (wrong physical road, worst on KMP, Southern Peripheral Road and Old Delhi–Gurgaon Road). 1,173 had no matching baseline cell. That leaves 20,198 usable training rows. In that training table: 2,313 rainy rows, 16,562 incident-affected rows, 6 holidays, 13/13 corridors.

4. How a prediction is produced

The map does not replay the latest CSV cell. Flask precomputes all 2,184 slots as

clip(baseline + predicted_residual, 0, 1)

and tags each cell residual_adjusted. The observed CSV is used to train, to build lag features, and to score the model. If the residual artifact is missing or its holdout skill is ≤ 0, model-backed endpoints return HTTP 503. There is no hand-written lookup table.

A static bundle (frontend/data/bundle.json) is the same grid dumped for the public site, so GitHub Pages or Vercel can serve the map without a Python process. Place search and connected routing for the trip planner run as small Vercel functions.

backend/test_api.py was run on 15 October 2026: 77 passed, 0 failed.

5. What the model is

The shipped model is a GradientBoostingRegressor that predicts the residual — how far a real hour departed from TomTom’s date-blind average — from weather, calendar, incidents, road class, and leak-safe lags (what that road was doing recently and a week earlier). File: models/forecast_residual_gbt.joblib, version forecast-gbt-2026-10-15, trained 15 October 2026 23:14. An MLP was tried on the same split and lost (holdout skill −1.07); it is not shipped. Dwarka Expressway has its own override estimator inside the artifact because that corridor does not behave like the others.

Why residual, not “predict congestion from scratch”

Rush hour already dominates the signal. The baseline already knows that. The model is asked only to explain the leftover: rain, a jam 200 m up the road, yesterday’s lag, a holiday. If it cannot beat the baseline on later days it never trained on, it must not ship. Skill is 1 − model MAE / baseline MAE. Skill ≤ 0 means the baseline alone is better.

6. How accurate it actually is

I score the shipped residual model on later live traffic, not on the rows it was trained on, and not on a number copied from an old README.

Train17,980 rows (16 Aug – 3 Oct 2026)
Test2,218 rows (4 Oct – 15 Oct 2026)
Baseline MAE (date-blind average vs live)0.1007
Model MAE (baseline + residual vs live)0.0461
Skill0.5417
Exact label agreement77.9% (n = 2,218)
Hour-ranking concordance88.1% (2,277 / 2,585 pairs; 154 corridor–date groups)
Production refit after that testall 20,198 usable rows
What those three scores mean

MAE — average miss on the 0–1 index. 0.046 is well under one label band (~0.11 wide).

Label agreement — how often Free / Moderate / Heavy / Severe matches the live reading. Random among four labels is 25%.

Hour-ranking concordance — given two hours on the same road and date, how often the model correctly says which is worse. 50% is a coin flip. This is closest to “when should I leave?”

The production estimator is then refit on all 20,198 rows. The numbers above are from the holdout-only snapshot, so they are not an in-sample exam on homework questions.

Earlier, with only 115 live rows, bootstrap-versus-observed ranking looked like 89%. On thousands of rows that diagnostic fell to about 57% ranking and about 42–43% labels. That was the date-blind average, not this residual model. I kept that episode in the story because it is why the residual model exists: the formula could not see rain, incidents, or yesterday.

What the site will not claim: a typical-week residual will not reproduce the worst jam you remember. The largest extra delay on the served typical-week grid is about 13 minutes (KMP Expressway, Monday 08:00 versus 22:00). A 30-minute one-off jam is a different question (a peak/quantile model), not a fatter number on this grid.

7. Decisions I would defend

Gate on skill, then ship. The trainer refused until rainy/dry/incident/day thresholds were met. After they were met, the model still had to beat the baseline on later days. Skill 0.54 cleared that. Skill ≤ 0 would have meant 503, not a silent fallback.

One source of truth. Corridor coordinates and road class live in corridors.py. Collectors, trainer and API all import it.

Incident matching by geometry. Distance to the digitised polyline, 300 m buffer from real incident-distance data, not a bounding box.

Fail loudly. 503 rather than a fabricated number; every cell carries an origin; tests fail if a default table appears.

Do not feed corridor identity as a cheat code. An earlier leave-one-corridor-out test on the first grid model got worse when corridor_id was a feature. The residual model may still encode it; time of day and lag dominate anyway.

8. Limitations

  • Served values are a typical week (baseline + residual for that weekday and hour), not “what NH-48 is doing this minute.”
  • Time of day still does most of the work. Rain flags barely moved this GBT; lag and incidents matter more for the leftover.
  • Dwarka Expressway remains a special case (construction traffic). It has an override in the artifact rather than being averaged away.
  • 3,119 live rows were unusable because the router snapped to the wrong length. Tightening via-points would recover training data, especially on KMP and SPR.
  • Collection is stopped at 15 October 2026, so the submitted model will not keep learning new weeks unless collection is turned back on and the model is retrained.
  • GitHub Actions schedules are best-effort and go dormant after 60 days of inactivity.

9. What I would do next

Turn collection back on, especially Monday rush hours, then retrain and re-run tools/evaluate_forecast.py. Recover the dropped length-mismatch rows. If the product needs “how bad can this hour get?”, train a labelled quantile/peak model instead of inflating You save on the typical-week grid.

10. Glossary

TermWhat it means here
Congestion indexFraction of travel time lost to traffic. 0 = empty, 0.5 = twice free-flow.
Free-flow timeEmpty-road travel time. The comparison for “vs empty.”
CorridorOne of the 13 tracked stretches.
SlotOne corridor × weekday × hour. 2,184 of them.
BaselineTomTom’s historical average for that slot. Date-blind.
ResidualLive index minus baseline. What the GBT predicts.
Skill1 − model MAE / baseline MAE. Positive means the model beats the average.
MAEMean absolute error on the congestion index.
ConcordanceHow often the worse of two hours is ranked correctly. 50% = coin flip.
Gradient boostingMany small trees in sequence, each correcting the last.
HoldoutLater days kept out of training and used only to score.
